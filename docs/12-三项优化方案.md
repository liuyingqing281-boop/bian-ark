## W1 邮箱验证码真实发送

### 现状
- 后端 `sendLoginCode`（`src/lib/notify.ts`）已集成 nodemailer：配了 `SMTP_URL` 就真实发邮件；未配时打印到日志。
- 非生产环境响应回显 `devCode`，前端自动回填——**这是开发便利，不是生产行为**。
- `@bian.dev` 测试域强制跳过 SMTP（防自动化测试连发被服务商限流）。

### 目标
用户收到真实邮件，手动输入验证码；界面不再自动回填。

### 改造点
| 层 | 改动 |
|---|---|
| 服务器配置 | `.env` 配 `SMTP_URL=smtps://user:pass@smtp.xxx.com:465` + `SMTP_FROM=彼岸 <no-reply@bianmuyuan.cn>`；阿里云/腾讯企业邮需开 SMTP 服务并生成授权码 |
| 后端 | 生产（`NODE_ENV=production`）本就不回显 devCode ✅ 无需改；补一条：生产且未配 SMTP 时 email 通道返回 503 `email_not_configured`（现在是静默 delivered:false，前端无感知） |
| 前端 | `auth.js` 的 devCode 自动回填分支保留（仅开发环境会收到 devCode）；生产环境自然不触发，无需改 |
| 短信 | 同理，`SMS_WEBHOOK_URL` 配好即真实发短信 |

### 验证口径
- 服务器配好 SMTP 后，用真实邮箱注册：收到「彼岸登录验证码」邮件 → 手动输入 → 登录成功。
- 未配置时前端 toast「邮件服务未配置，请先用手机号」。

## W3 「想念」对话双模式

### 两种模式定义

| | 第三方模式（现状，默认） | 模仿模式（新增） |

| AI 身份 | 纪念性助手，明确「不是 TA 本人」 | 以角色第一人称与用户对话（「我」= TA） |
| 措辞 | 涉及 TA 想法用「可能/大概」推测语气 | 用 TA 的语气、口头禅直接回应 |
| 依据 | 同样只依据记忆资料，禁止编造 | 同样只依据记忆资料；资料外的事用角色口吻承认「记不清了」 |

## W4 聊天沉淀为记忆（对话即资料）

> 2026-08-23 追加。用户要求：聊天的信息会被记录下来作为记忆，以后聊天会参考之前的聊天内容。

### 设计：两层机制

| 层 | 机制 | 说明 |
|---|---|---|
| 短期上下文 | 对话时注入最近 K 条聊天记录 | `buildChatSystemPrompt` / `buildRoleplaySystemPrompt` 增加「近期对话」段：取本馆本人最近 20 条 `chat_messages`（已有表 ✅），让 AI 记得上次聊到哪 |
| 长期沉淀 | 聊天中的新信息抽取为记忆 | 每轮对话后异步调用 LLM 判断：用户这句话是否包含关于 TA 或「我和 TA」的新事实；有则以 `section='chat'`、`source='chat'` 写入 `memories` 表（已有 ✅），后续对话经资料注入自然被参考 |

### 规则
1. 抽取只从**用户说的话**里提取（AI 的回应不回流，防止自我强化编造）。
2. 抽取出的记忆进 `memories` 表与手写记忆同权，出现在屏04「记忆」页——分区显示为「💬 聊天中记起」，可删除（复用现有删除）。
3. 抽取结果同样过 `moderateText`；抽取失败静默跳过，不影响对话主链路。
4. 隐私边界：只沉淀**与 TA 相关的事实**，不记录用户的情绪倾诉原文（提示词中明确禁止逐字搬运倾诉内容）。
5. 用户可在设置中关闭：settings 加键 `chatMemory`（默认 true），PATCH /api/me/settings 白名单加该键。

### API / 数据仓库
- 对话接口契约不变（内部增强）；`GET /api/memories` 响应的 `section` 新增取值 `chat`。
- `memories.source` 新增取值 `'chat'`（现为 manual/wizard），无需迁移（TEXT 列）。
- 无新表。

## W6 生图百分比进度条

> 2026-08-23 追加。用户要求：生成图片时能看到真实进度百分比。

### 现状
`POST /api/items/generate` 是**同步**接口：循环生成 4 张图后一次性返回，期间前端无法知道进度。

### 目标方案：异步任务 + 轮询（真实进度）
1. 生图改异步：`POST /api/items/generate` 立即返回 `{ jobId, status:"processing" }`，后台逐张生成，每完成一张更新任务行。
2. `ai_generation_jobs` 表加进度列（迁移 019 一并做）：
   ```sql
   -- @add-column ai_generation_jobs total INTEGER DEFAULT 4
   -- @add-column ai_generation_jobs completed INTEGER DEFAULT 0
   ```
3. 新增查询接口（08 文档早已预留 `GET /api/items/generate?jobId=` 契约）：
   ```json
   { "jobId", "status": "processing|done|failed", "completed": 2, "total": 4,
     "candidates": [/* 已完成的图，可先露 thumbnail */], "error": null }
   ```
4. 前端每 1.5s 轮询，进度条 = `completed/total`；全部完成进入选图；失败显示「生成失败，点击重试」。
5. 幂等键机制不变：同 key 重进直接返任务现状，断网重连可续看进度。

### 降级兜底
若轮询接口异常超过 30s，前端 toast「生成有点慢，仍在继续」继续轮询，不假装 100%。**不做纯前端假进度条**（进度必须来自后端真实 completed 数）。
