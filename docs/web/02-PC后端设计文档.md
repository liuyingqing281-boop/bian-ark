# 彼岸 · PC 端后端设计文档

> 依据：`docs/web/01-PC前端设计文档.md`、`docs/08-API接口说明书.md`、`docs/09-数据库设计.md`。
> **核心结论：PC 端与移动端共用同一套后端服务与数据库，不新建独立后端。** 本文只定义支撑 PC 体验所需的后端增量：视图模型扩展、分页契约、会话与 SSR 策略、性能与缓存。所有既有接口（08 文档 ✅ 项）原样复用，契约只增不减。

---

## 一、总体架构

```
┌──────────────┐   ┌──────────────┐
│  移动端 Web   │   │  PC 端 Web    │
└──────┬───────┘   └──────┬───────┘
       │   同一套 REST API（/api/*，JSON，Cookie 会话）
       └────────┬─────────┘
        ┌───────▼────────┐
        │ Next.js 后端    │
        │ · 适配层（camelCase 视图模型装配 / maskName 打码 / viewerRole 权限）
        │ · 业务层（memorials / memories / messages / tribute / chat / items / groups / garden）
        │ · 横切：moderateText 审核 / 限长 / 限频 / 错误码
        └───────┬────────┘
        ┌───────▼────────┐
        │ SQLite(bian.db) │  Stripe │  LLM 服务 │  对象存储(图片)
        └────────────────┘
```

- **零表结构变更**：PC 端所需数据均已由 09 文档的表与视图模型（F1–F6）覆盖；本文不新增表，仅对个别视图模型做**只增不减**的字段扩展（见 §三）。
- 设备形态区分**只发生在前端**；后端不引入 `device=pc` 之类的分支逻辑，避免契约分叉。唯一例外：分页参数默认值（§四）。

## 二、会话与鉴权

- 沿用 08 §二：验证码 / 微信扫码换 Cookie 会话；PC 扫码场景为主，需保证 `/api/auth/wechat/*` 在桌面浏览器下的回调与轮询可用（✅ 已有，回归即可）。
- PC 特有考量：
  - Cookie `SameSite=Lax` + `Secure`；会话有效期与移动端一致，不做「记住我」延长（纪念产品安全优先）。
  - 访客态只读公开内容，接口行为与移动端完全一致。

## 三、视图模型扩展（只增不减）

| 视图模型 | 新增字段 | 服务场景 | 说明 |
|---|---|---|---|
| F1 MemorialView | `appellation` 已含；无新增 | — | PC 顶栏「和+称谓+说说话」直接复用 |
| F3 FeedView | `nextCursor?: string` | 「最近的纪念」分页 | PC 右栏展示 5 条 + 「查看全部」进入分页列表；移动端忽略该字段即可 |
| F5 ChatHistoryView | `nextCursor?: string` | 对话侧板历史上拉加载 | 侧板高度大、滚动多，需游标分页（当前 history 接口 🟡 待开，一并纳入契约） |
| F6 OrderView | 无新增 | 订单表格分页复用通用分页参数 | 见 §四 |

- 打码（`maskName`）、`viewerRole`、UTC 时间串下发等装配层职责不变；前端换算时区（承接 08/09 已知待办 ③，PC 端同样处理）。
- **禁止**为 PC 端返回未打码字段或额外权限字段。

## 四、分页契约（PC 增量）

宽屏列表变长，以下接口补齐统一游标分页：

```
GET /api/hall/feed?memorialId=&limit=20&cursor=<opaque>
GET /api/hall/chat/history?memorialId=&limit=30&cursor=<opaque>   （🟡 待开接口，直接按本契约实现）
GET /api/me/orders?limit=20&cursor=<opaque>                        （🟡 待开接口）
```

- 响应统一：`{ "items": [...], "nextCursor": "..." | null }`，`nextCursor=null` 表示到底。
- `limit` 上限 50，缺省 20；游标不透明串（后端按 `createdAt+id` 编码），倒序。
- 移动端不传 `cursor` 时行为不变（返回首页数据），兼容零成本。

## 五、对话与 LLM 链路

- 完全复用 `POST /api/hall/chat`（✅ 含 evidence / askMemory / moderation / guest 冒烟）。
- PC 侧板与移动端对话页**共享同一份历史**（同一 `memorialId` 维度），用户换端可续聊——后端无需区分，历史接口按 memorialId+用户取数即可。
- 建议（非阻塞）：`POST /api/hall/chat` 后续支持 SSE 流式输出，PC 宽屏长回复体验更好；V1 仍走一次性返回 + 三点呼吸动画，不阻塞上线。
- `503 llm_unavailable`、敏感内容「轻轻带过」、推测标识等由后端原样下发，前端只渲染。

## 六、性能与缓存

| 项 | 策略 |
|---|---|
| 静态资源 | PC 端图片（头像/封面/祭品/生成物）走 CDN + `?w=` 多档尺寸（Hero 封面 1600w、卡片 400w、头像 128w）；`Cache-Control: immutable` + 内容哈希 |
| 接口缓存 | `GET /api/memorials/[id]`、`GET /api/timeline` 可 `private, max-age=30`；feed/chat/orders 不缓存 |
| SSR | PC 首页 SEO/首屏走 SSR（纪念馆公开信息）；对话侧板、留言提交等交互区 CSR |
| 限频 | 对话与「帮我写」沿用移动端限额（按用户+日），PC 不放宽 |
| 审核 | 所有写接口先过 `moderateText`，`422 content_rejected`；规则与移动端零差异 |

## 七、安全与合规

- 越权与可见性：服务端强制，悄悄话过滤不泄露存在性（已实现，回归覆盖 PC 场景）。
- PC 端多标签页场景：写操作幂等键沿用（`POST /api/items/generate` 幂等已冒烟）；`POST /api/tribute` 付费必须先验 `order_id` 已支付。
- 日志：PC 端埋点上报与移动端共用通道，维度加 `platform: "web-pc"`（仅埋点，不进业务逻辑）。
- 外链安全：`/api/items/claim` 外部 URL 拦截规则沿用。

## 八、星海与合馆后端增量（2026-08-23 新增）

> 依据：墓园规格 §8（星海）、13 号方案（灯阵）、09 文档 B17/F7/F8/M8/M9。契约明细落在 08 文档 §3.13，本文只定装配与策略。

- **新表依赖**：`halls` + `memorials.hall_id`（M8/M9），是本轮唯一表结构变更；既有接口契约不受影响。
- **视图装配**：新增 `toHallView`（F7）与 `toGardenSeaView`（F8）装配函数进 `src/lib/view-models.ts`；`candleLit` 分馆/分人推断复用既有 24h 窗口逻辑，仅聚合维度从单馆变为 `hall_id`。
- **星海分片**：`GET /api/garden/starsea` 支持 `?zone=&bbox=` 分片参数服务 LOD；响应可 `private, max-age=15` 短缓存（明灭状态允许秒级延迟）；清明脉冲期静态化快照（NFR-02 降级预案同源）。
- **择位写路径**：`PATCH /api/halls/[id]/garden-pos` 仅馆主；服务端做空位冲突检测（同位 ±ε 已有星群则 `409 position_conflict`，前端引导微调）；`in_garden=1` 前置校验馆可见性为 public。
- **馆内摆位**：`PATCH /api/halls/[id]/layout` 仅馆主，写 `halls.layout_json`；与园级择位互不干扰。
- **合祭**：`POST /api/halls/[id]/offer-all` 事务内对馆内 N 位人物各落一条 `tributes`（同批次号/同 `order_id` 关联）；任一失败整体回滚；审核与限频规则同单供。
- **红线**：F7/F8 装配层不下发访问量、热度字段；择位/摆位不计费不限次；名人星域 `zone='official'` 仅平台后台可写。
