# 16 · 部署优化方案（2026-09-07，对应 15 号现状报告）

> 分级原则：P0=安全（当天）· P1=发布可靠性（本周）· P2=运维自动化（两周）· P3=架构卫生（择期）。
> 每项：问题 → 方案 → 工作量 → 验收标准。所有改动走「先文档、后代码、验证、发布」既有节奏。

## P0 · 安全（当天可完成）

### P0-1 禁用已暴露的主账号 AccessKey
- **问题**：一对主账号 AK 完整出现在聊天记录（15 号报告 §六-1）
- **方案**：控制台「头像 → AccessKey 管理」禁用 `LTAI…Qrmz`（保留 RAM 子账号与否随意——对轻量服务器均无用）；后续如需 API 再建新对
- **工作量**：2 分钟（控制台操作；可由助手驱动浏览器代办）
- **验收**：该 AK 调任意 API 返回 InvalidAccessKeyId.NotFound

### P0-2 生产屏蔽原型/演示路由
- **问题**：`/concept`（根路径默认落点）、`/proto/*`、`/prototype`、`/proto-zcode`、`/showreel` 全部暴露在生产域名（15 号报告 §四），且 /proto 依赖 CSP 放行外部 CDN
- **方案**：`src/proxy.ts` 增加环境开关 `ENABLE_PROTO_ROUTES`（生产缺省=false → 404；本地 dev 保留）；**不删任何代码**，演示需要时可在预览环境打开。同时收紧 `next.config.ts:30` 的 CSP（去掉 cdn.tailwindcss.com——原型自带编译后样式即可，或随路由屏蔽一并失效）
- **工作量**：0.5 天（proxy.ts 分支 + e2e 一条「生产模式 404」断言）
- **验收**：线上访问五个路由均 404；本地 dev 全部正常；既有 e2e 全绿

### P0-3 数据库定时备份
- **问题**：备份只在发布时产生一次（15 号报告 §五），磁盘单点
- **方案**：服务器 crontab：每日 04:00 `cd /var/www/bian && npm run db:backup`，并加一条 `find data/backups -name 'bian-*.db' -mtime +7 -delete`（保留 7 天）；先统一备份目录口径（见 P1-4），cron 直接落 `data/backups`
- **工作量**：0.5 小时（SSH 上两行 crontab）
- **验收**：`crontab -l` 可见两条；次日在 data/backups 出现新备份且第 8 天自动清理

## P1 · 发布可靠性（本周）

### P1-1 一条龙发布命令 `tools/release.mjs`
- **问题**：发布 = 本地四步手工 + 服务器一步 + 验证若干（15 号报告 §二），人工易错（845MB 废包事故即例证）
- **方案**：本地脚本串起：检查工作区干净与当前 commit → 停本地 dev 占用 → `npm run build` → 打包（排除 .next/cache）→ `scp` 上传 → 远程 `apply-release.sh` → 远程拉回验证（health/starsea/db:verify/git rev）→ 本地输出一份 markdown 发布报告。走已打通的 `~/.ssh/bian_deploy` 密钥；npm script：`"release": "node tools/release.mjs"`
- **工作量**：1 天
- **验收**：从「说发布」到「报告产出」一条命令、零人工；故意制造失败（如停掉服务器）能给出明确错误

### P1-2 产物-代码一致性校验
- **问题**：.next 来自本地任意 commit 的构建，服务器 `git reset --hard origin/master` 各自为政，存在错位窗口（15 号报告 §八-中）
- **方案**：release.mjs 打包时把 `COMMIT`（git rev-parse）写入 tar 内（`.next/RELEASE_COMMIT`）；apply-release.sh 解包后读出并与 `git rev-parse HEAD` 比对，不一致直接中止发布（退出码非 0，保留旧 .next）
- **工作量**：0.5 天
- **验收**：构造不一致（tar 内写旧 commit）时发布中止且旧站不受影响

### P1-3 一键回滚
- **问题**：无回滚脚本，仅 deployment.md:57-63 手工步骤（15 号报告 §八-中）
- **方案**：apply-release.sh 解包前 `mv .next .next.prev`（保留上一版）；新增 `deploy/rollback.sh`：`.next.prev` ↔ `.next` 互换 + pm2 restart + 可选恢复最近 db 备份（列出让运维选择，不自动覆盖）；release.mjs 报告中打印回滚命令
- **工作量**：0.5 天
- **验收**：演练一次回滚：站点回到上一版本、数据不丢（db 备份在场不覆盖）

### P1-4 备份目录口径统一
- **问题**：BACKUP_DIR / DB_BACKUP_DIR / 手册三处矛盾，`.env` 的 BACKUP_DIR 不生效（15 号报告 §五）
- **方案**：统一为 `data/backups`：`tools/backup.mjs` 改读 `DB_BACKUP_DIR`（缺省同 db-migrate）；`production.env.example` 删除误导项并注明；07 手册 §一同步
- **工作量**：0.5 小时
- **验收**：`npm run backup` 与 `npm run db:backup` 落同一目录；grep 无残留旧口径

## P2 · 运维自动化（两周）

### P2-1 外部拨测告警
- **问题**：站点挂了没人知道（无监控）
- **方案**：UptimeRobot（免费）盯 `https://bianmuyuan.cn/api/health`（5 分钟间隔），告警发邮箱；如需更细，加 `/zh/garden` 200 监控
- **工作量**：0.5 小时（网页配置）
- **验收**：人为停 pm2 一分钟，收到告警邮件

### P2-2 日志轮转与磁盘清理
- **问题**：/var/log/bian 无限增长风险；data/backups 与未来 .next.prev 也占盘
- **方案**：logrotate 配置（daily、rotate 14、compress）；crontab 加每周清理（备份>7 天已由 P0-3 覆盖，.next.prev 只保留 1 份天然限量）
- **工作量**：0.5 小时
- **验收**：logrotate -d 语法过；一周后日志被压缩轮转

### P2-3 生存性确认
- **问题**：服务器重启后 pm2/certbot/nginx 是否自愈未验证过
- **方案**：确认 `pm2 startup` 已配置（输出对比 systemd 单元）；在低峰期做一次计划内重启演练，记录恢复时间；certbot.timer 已自动（现状确认）
- **工作量**：1 小时（含演练窗口）
- **验收**：重启后 1 分钟内 https 恢复 200，无需人工

## P3 · 架构卫生（择期，按产品节奏）

### P3-1 首页收口
- **问题**：双首页（`/`=概念稿、产品在 /garden）混淆用户与 SEO（15 号报告 §四）
- **方案**：产品决策——对外发布前把 `/` 指向 `/zh`（概念稿退到 `/concept` 显式路径或直接随 P0-2 屏蔽）；`/[lang]` 改为真首页或直接重定向 `/[lang]/garden`
- **工作量**：0.5 天（含文案）；**需用户拍板方向**

### P3-2 admin 鉴权统一到中间件层
- **问题**：admin API 逐路由 requireAdmin，页面靠 API 拒绝（架构梳理 §3）——风格分散、新路由易漏
- **方案**：proxy.ts 对 `/[lang]/admin` 与 `/api/admin` 统一做会话+ADMIN_EMAILS 校验（保留 API 内校验作纵深）
- **工作量**：0.5 天 + e2e

### P3-3 /uploads 流式化与对象存储适配
- **问题**：readFileSync 全量入内存（大文件冲击 400M 预算）；STORAGE_PROVIDER 仅 local 实现（15 号报告 §三）
- **方案**：route 改 `fs.createReadStream` +ETag/缓存头（1 小时见效）；中期按既有 STORAGE_PROVIDER 接口补 OSS Adapter（上传直传+签名回链），备份同步受益
- **工作量**：流式 0.5 天；OSS 2-3 天

### P3-4 文档与脚本归一
- **问题**：deployment.md 与 07 手册双轨、deploy.sh 弃用未删、步骤编号错序（15 号报告 §八-低）
- **方案**：07 手册为唯一真相源（deployment.md 并入或标注「历史参考」）；删除 deploy.sh；修正 [4.5/7] 编号；release-checklist 与 release.mjs 报告打通
- **工作量**：0.5 天

## 实施顺序建议

```
当天：P0-1（你/我控制台禁 AK）→ P0-3（crontab）→ P0-2（proxy 开关）
本周：P1-1 → P1-2 → P1-3 → P1-4（一次发布内全部带上线）
两周：P2-1 → P2-2 → P2-3
择期：P3-1（先拍板首页方向）→ P3-4 → P3-2 → P3-3
```

总计：P0 约 1 天、P1 约 2.5 天、P2 约 1 天、P3 约 4-5 天。P0/P1 全部完成后，「发布」收敛为一条命令 + 一份自动报告 + 一键回滚。
