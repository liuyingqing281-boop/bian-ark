# 彼岸前端交互优化方案

## 1. 方案目标

本方案针对「彼岸 · 线上墓园」的首页、公共墓园、纪念馆详情、登录、会员和个人管理流程，目标是让用户能够：

- 快速理解页面当前状态和下一步操作；
- 在桌面端和移动端稳定完成浏览、搜索、创建、上传、供奉和管理；
- 在异步请求、失败、权限不足和空数据场景下得到明确反馈；
- 使用键盘、触摸和辅助技术完成核心流程；
- 在保持庄重、克制的纪念场景氛围下，减少不必要的等待和迷失。

## 2. 项目现状

技术栈为 Next.js 16.3、React 19、TypeScript 7、Tailwind CSS v4 和 Three.js。现有页面已有暗色石材/琥珀色视觉基础、2.5D/3D 花园、响应式导航和部分无障碍标记。

本次检查确认的主要问题：

| 区域 | 现状 | 影响 |
| --- | --- | --- |
| 全局异步操作 | 部分上传、保存、会员操作缺少统一错误和成功反馈 | 用户不知道请求是否完成，失败后无法重试 |
| 移动端导航 | 390 px 下导航分两行并横向排列，入口密集 | 首屏内容被挤压，菜单容易误触或被忽略 |
| 公共墓园 | 搜索、视图切换、抽屉、详情和供奉状态集中在一个组件 | 状态关系复杂，前进/后退和恢复现场困难 |
| 触控体验 | 部分文字按钮和返回入口小于推荐触控尺寸 | 移动端操作成本高 |
| 危险操作反馈 | 仍有 `alert()`，删除/退出等操作缺少统一确认层 | 反馈打断流程，风险说明不充分 |
| 动效策略 | 场景动效较丰富，但状态反馈不统一 | 视觉有氛围，操作结果却不够明确 |
| 空状态和异常 | 页面有基础空状态，但搜索、网络失败和权限状态不统一 | 用户缺少下一步行动指引 |

## 3. 交互原则

### 3.1 状态优先

每个可提交操作必须明确表达 `idle`、`busy`、`success`、`error` 和 `disabled` 状态。状态变化优先使用文字和控件变化表达，动效只作辅助。

### 3.2 一个主动作

每个视图只保留一个最重要的主动作。主按钮使用琥珀色强调，次要操作使用低对比度按钮，危险操作使用红色但不与主动作竞争。

### 3.3 就地反馈

反馈出现在操作附近；跨页面或全局事件使用 Toast。成功反馈不阻塞用户继续浏览，错误反馈必须包含可执行的重试或修复动作。

### 3.4 可逆优先

删除、退出群组、轮换邀请链接等操作需要二次确认；可恢复操作优先提供撤销，而不是立即弹出复杂流程。

### 3.5 尊重场景

避免大面积弹窗、连续闪烁、自动播放声音和过度视差。纪念内容优先于装饰性动效。

### 3.6 输入设备平等

核心操作同时支持鼠标、键盘和触摸。所有交互目标最小尺寸为 44×44 px，焦点状态不能只依赖颜色变化。

## 4. 统一交互基础设施

### 4.1 反馈组件

新增或统一以下基础组件：

- `Toast`：成功、提示、错误三种级别；支持自动消失、手动关闭和 `aria-live`；
- `ConfirmDialog`：标题、影响说明、取消、确认；危险确认按钮明确标注动作；
- `InlineStatus`：表单或上传控件旁显示进行中、成功、失败和重试；
- `Skeleton`：首页卡片、花园列表、媒体列表的稳定占位；
- `EmptyState`：说明当前没有内容，并给出下一步按钮；
- `ErrorState`：区分网络错误、权限错误和服务错误，避免统一显示“失败”。

建议提供 `useAsyncAction` 或等价的统一状态封装，禁止各组件重复编写无反馈的 `fetch` 流程。

### 4.2 按钮和链接规范

- 页面跳转使用链接，数据变更使用按钮；
- 提交期间按钮保持尺寸不变，显示 spinner 和进行中文案；
- 禁用态必须同时具备视觉和语义表达，并说明原因；
- 图标按钮必须有 `aria-label` 和 tooltip；
- 重要操作不只在 `hover` 时出现，移动端也必须可发现。

### 4.3 表单规范

- 输入框使用 `label`、示例 placeholder 和字段级错误；
- 错误显示在字段附近，并将焦点移至第一个错误字段；
- 校验区分格式错误、必填错误和服务端错误；
- 验证码输入支持自动聚焦、粘贴、退格回退和 Enter 提交；
- 离开未保存表单时给出明确提示。

### 4.4 动效规范

| 类型 | 时长 | 用途 |
| --- | ---: | --- |
| 控件反馈 | 120–160 ms | hover、focus、pressed、颜色变化 |
| 面板切换 | 180–240 ms | 抽屉、详情、Toast |
| 场景动效 | 低频、可暂停 | 烛光、萤火、云雾等氛围 |

统一使用 `transform` 和 `opacity`，避免对布局属性做高频动画。实现 `prefers-reduced-motion: reduce`：关闭装饰性循环动画，保留必要的状态变化。

## 5. 页面级优化

### 5.1 首页

目标：让首次访问者在 5 秒内理解产品，并能进入公共墓园或创建纪念馆。

- 首屏只保留“走进公共墓园”和“创建纪念馆”两个主入口；
- 分类筛选使用真正的 segmented control，当前项有 `aria-current` 或选中语义；
- 分类切换后保留滚动位置，并在列表更新时显示轻量 loading；
- 卡片统一显示头像、姓名、日期和悼词摘要，长文本截断但可在详情查看；
- 空列表提供“清除筛选”和“创建纪念馆”操作；
- 图片使用稳定宽高比和懒加载，避免列表跳动；
- 键盘 Tab 顺序按品牌、主入口、筛选、内容卡片排列。

### 5.2 公共墓园

目标：快速找到墓位，并完成一次缅怀或供奉。

- 顶部工具栏固定为：返回、搜索、2.5D/3D 切换；
- 搜索支持清空、匹配计数、无结果建议，输入状态可通过 URL 查询参数恢复；
- 2.5D/3D 切换保留搜索条件、选中墓位和抽屉状态；
- 墓位选中后，场景对象、卡片和详情面板同步高亮；
- 抽屉提供 `collapsed / half / full` 三态，移动端支持拖拽和上滑；
- 详情流程使用状态机：`list → detail → offer → success`，返回按钮只回退一个业务层级；
- 供奉成功后显示结果、供奉类型和留言摘要，提供“继续浏览”和“再次供奉”；
- 3D 加载失败时自动回退到 2.5D，并保留错误说明和重试入口；
- 场景对象具备键盘可达性、可见焦点和明确的 `aria-label`。

### 5.3 纪念馆详情

- 封面和头像上传采用同一套上传状态组件；
- 上传前显示文件类型、大小限制和替换说明；
- 上传过程中保留预览，成功后局部更新，不让用户等待整页刷新；
- 上传失败显示具体原因和重试按钮；
- 供奉、时间线、媒体等模块使用一致的成功反馈；
- 长内容分段展示，移动端避免把主信息藏在过深的折叠层级；
- 页面标题、返回入口和当前纪念馆名称保持稳定，便于辅助技术定位。

### 5.4 登录

- 邮箱、短信切换使用 tabs/segmented control，并明确当前渠道；
- 请求验证码后显示倒计时、重新发送和修改目标入口；
- 验证码错误保留输入内容，过期时只提示重新获取；
- 网络错误可直接重试，不清空用户已经填写的目标；
- 登录成功后回到用户原本想访问的页面；
- 任何验证码、密码和敏感字段不得写入日志或 Toast。

### 5.5 会员页

- 用站内 Dialog/Toast 替换 `alert()`；
- 已登录、未登录、演示模式和支付处理中四种状态分别设计；
- 支付按钮在支付请求期间锁定，避免重复提交；
- 支付失败显示重试和联系客服/返回入口；
- 价格、权益和当前订阅状态在移动端按同一顺序呈现。

### 5.6 个人管理页

- 将“我的纪念馆”“媒体”“时间线”“群组”分为清晰的 tabs 或章节导航；
- 保存、上传、邀请链接复制和成员操作均使用统一状态反馈；
- 删除、退出、解散和转让使用二次确认，并显示目标名称；
- 复制邀请链接成功后显示短 Toast，失败时提供手动复制提示；
- 列表支持空状态、加载状态和权限不足状态；
- 修改表单支持未保存离开提醒。

## 6. 状态模型和数据流

### 6.1 异步操作状态

所有 mutation 按以下模型实现：

```ts
type AsyncState<T> =
  | { status: "idle" }
  | { status: "busy"; requestId: string }
  | { status: "success"; data: T; message?: string }
  | { status: "error"; message: string; retryable: boolean };
```

要求：请求开始时生成 `requestId`；只允许最新请求更新 UI；组件卸载后不得写入已失效状态；重试必须复用原始参数。

### 6.2 花园状态机

```text
浏览列表
  └─ 选择墓位 → 查看详情
                  └─ 点击供奉 → 选择供奉物/留言
                                  ├─ 提交中
                                  ├─ 成功 → 继续浏览 / 再次供奉
                                  └─ 失败 → 重试 / 返回详情
```

搜索条件、视图模式、选中 ID 和抽屉阶段应成为可序列化状态；适合放入 URL 的状态使用 query 参数，其余局部状态使用组件状态或 Zustand。

## 7. 响应式和无障碍验收

必须验证以下视口：375×812、390×844、428×926、768×1024、1280×800。

- 页面 `scrollWidth` 不得超过视口宽度；
- 核心按钮和输入框尺寸不低于 44×44 px；
- 键盘可访问所有核心操作，焦点顺序合理；
- 对话框打开后焦点进入对话框，关闭后回到触发按钮；
- Toast 使用 `aria-live="polite"`，错误使用合适的 assertive 级别；
- 颜色对比度满足 WCAG AA；
- `prefers-reduced-motion` 下无持续装饰动画；
- 3D 不可用时仍能完成搜索、查看详情和供奉。

## 8. 性能和稳定性要求

- 首屏主内容优先于 3D 场景加载；
- Three.js 使用动态导入，加载期间显示稳定 skeleton；
- 图片指定尺寸或比例，避免 CLS；
- 列表超过 50 项时采用分页、虚拟化或增量加载；
- 搜索输入使用 150–250 ms debounce，并取消过期请求；
- 动效只使用合成层友好的属性；
- 关键交互错误写入可观测日志，但不得包含敏感数据。

## 9. 实施阶段

### Phase 1：交互基础（P0）

1. 建立 Toast、Dialog、InlineStatus、Skeleton、EmptyState、ErrorState；
2. 统一 `useAsyncAction` 和错误映射；
3. 替换会员页 `alert()`；
4. 修复上传、保存、供奉的失败和重试流程。

### Phase 2：核心流程（P0）

1. 拆分 `GardenViewSwitch` 的列表、详情、供奉面板；
2. 引入花园状态机和 URL 可恢复状态；
3. 完成抽屉触摸手势、键盘操作和 3D 回退；
4. 优化移动端导航结构。

### Phase 3：表单与管理（P1）

1. 统一登录验证码流程；
2. 补齐个人管理页确认、复制、未保存提醒；
3. 统一空状态、权限状态和网络异常状态；
4. 完成焦点管理和 aria 语义。

### Phase 4：视觉与性能（P1/P2）

1. 建立语义化颜色、间距、阴影和圆角 token；
2. 统一微交互时序；
3. 补齐 reduced-motion；
4. 做图片、3D 和列表性能优化。

## 10. 测试矩阵

### 自动化测试

- 首页筛选、空状态和卡片跳转；
- 花园搜索、视图切换、抽屉三态和返回层级；
- 供奉成功、失败、重复提交和重试；
- 上传成功、失败、禁用和局部刷新；
- 登录验证码倒计时、错误和回跳；
- 危险操作取消与确认；
- 键盘 Tab、Enter、Escape 和焦点回收。

### 手工验收

- iOS Safari 和 Android Chrome 触摸滑动；
- 弱网、接口 500、超时和重复点击；
- 关闭 JavaScript 或 3D 能力后的降级体验；
- 深色主题、系统 reduced-motion 和高对比度设置；
- 中英文切换后文本不溢出、不遮挡。

## 12. 交付物

- 统一交互组件和状态 Hook；
- 拆分后的花园列表、详情、供奉模块；
- 更新后的导航、登录、上传和管理流程；
- Playwright 核心流程测试和移动端测试；
- 交互 token 与 reduced-motion 样式；
- 本方案对应的变更清单、测试结果和已知限制。

## 13. 不做事项

- 不为了“更活泼”增加大面积视差、自动播放声音或持续闪烁；
- 不在没有用户价值的地方引入新状态管理库；
- 不把所有信息塞进弹窗或抽屉；
- 不以隐藏错误、延长 timeout 或禁用测试来掩盖不稳定行为；
- 不在本轮修改后端业务规则、支付规则和数据模型。
