# 彼岸 · 数据库设计（前后端分离版）

> 依据：《前端具体设计流程.md》交互拆解 + `migrations/001–014` 现有 schema 实测核对。
> 本文分上下两篇：**上篇 · 前端数据设计**（前端只面对「数据视图契约」，不感知物理表、不感知 SQL）；**下篇 · 后端数据设计**（物理表、索引、迁移、权限落库规则）。
> 分界原则：前端消费的是「接口返回的视图模型」，后端负责「视图模型 ↔ 物理表」的装配与拆解；前端永不直接引用表名/字段物理名以外的知识。

# 上篇 · 前端数据设计（视图契约层）

> 前端所有页面数据来自 6 个视图模型（ViewModel），与《API 接口说明书》响应体一一对应。前端开发只需本篇。

## F1. 纪念馆视图 `MemorialView` — 01 屏首页 / 03 屏说明页 / 04 屏顶栏

```ts
interface MemorialView {
  id: string;
  name: string;             // TA 的名字
  appellation: string;      // 称谓「爷爷」，空则前端回落「TA」【待确认⑧】
  birthDate: string;        // 1940
  deathDate: string;        // 2023
  epitaph: string;          // 寄语
  avatarUrl: string;
  viewerRole: 'owner' | 'collaborator' | 'member' | 'guest'; // 决定 ⋯ 菜单与【+】可见性
  candleLit: boolean;       // 你点的灯还亮着【待确认①】
  candleLitHours: number;
}
```

**页面消费规则**：
- 01 屏 ⋯ 菜单：`owner/collaborator` 显示 分享/编辑/协作；其余显示 举报。
- 01 屏时间线【+】、05 屏记忆编辑/删除：仅 `owner/collaborator`。
- 04 屏标题：`和 ${appellation || 'TA'} 说说话`。

## F2. 时间线视图 `TimelineItem[]` — 01 屏「TA 的人生」

```ts
interface TimelineItem {
  id: string;
  year: string;
  title: string;
  description: string;
  imageUrl: string | null;  // 图文卡片「1978 · 青岛看海」【待确认⑨】
```

按 year 升序渲染；空数组 → 空状态「还没有记录 TA 的故事」+ 引导按钮（仅管理者可点）。

## F3. 纪念流视图 `FeedItem[]` — 01 屏「最近的纪念」

```ts
interface FeedItem {
  kind: 'tribute' | 'message';
  icon: string;            // 🌸💬🕯️
  label: string;           // 「献上鲜花 / 留下思念 / 写下悼文」
  senderMasked: string;    // 已打码「李**」，前端直接使用，禁止自行拼接原文
  message: string;
  isMine: boolean;         // 悄悄话条目「我」的展示依据
  isBurning: boolean;
  createdAt: string;       // UTC，前端负责时区换算 + 相对时间「2 小时前」
}
```
超过 5 条折叠为「查看全部纪念」；空数组 → 「成为第一个纪念 TA 的人」。

## F4. 记忆档案视图 `MemoryArchiveView` — 05/06 屏

```ts
type MemorySection = 'personality' | 'relation' | 'likes' | 'speech' | 'profile';
interface MemoryArchiveView {
  total: number;                                   // 「已建立 32 条记忆」
  sections: Record<MemorySection, MemoryEntry[]>;  // 5 分区固定齐全，空分区给 []
}
interface MemoryEntry { id: string; section: MemorySection; content: string;
  source: 'manual' | 'chat'; createdAt: string; }
```
- 分区元数据（图标/标题/空状态文案）为前端常量，不下发：
  `personality` 👤 TA 是怎样的人｜`relation` ❤️ 我和 TA（关系记忆，视觉强调）｜`likes` 🎵 TA 喜欢什么｜`speech` 💬 TA 怎么说话｜`profile` 📄 基础资料。
- 写操作（增/改/删）仅在 `viewerRole ∈ {owner, collaborator}` 时渲染入口；「补充记忆」入口例外，见 F5。

## F5. 对话视图 `ChatReply` — 04 屏

```ts
interface ChatReply {
  text: string;
  evidence: { memoryId: string; quote: string; createdAt: string } | null; // null = 不渲染依据链接
  inferred: boolean;        // true → 渲染「基于 TA 的资料推测」角标（不可关闭）
  askMemory: boolean;       // true → 渲染「添加一段关于 TA 的记忆」按钮
  followupQuestion: string | null;  // 引导问题「爷爷什么时候开始喜欢钓鱼？」
}
```
状态机（前端本地）：`sending → streaming(正在想你问的话…) → done | error(重试) | blocked(轻轻带过)`。历史记录 `ChatHistoryItem[]` 结构同 role+content+evidenceMemoryId【待确认④】。

```ts
interface ItemView {        // 宫格
```

## F7. 合馆灯阵视图 `HallView` — 多人馆场景（2026-08-23 新增，FR-02b）

```ts
interface HallView {
  id: string;
  name: string;              // 馆名
  motto: string;             // 馆训，空串不渲染
  skin: 'lanterns' | 'ancestral';
  viewerRole: 'owner' | 'collaborator' | 'member' | 'guest'; // 馆级，决定摆位/管理入口
  lamps: LampView[];         // 1~6 盏；>6 不合法（后端不产生）
}
interface LampView {
  memorialId: string;
  nameMasked: string;        // 访客态已打码，馆主态为原文（由 viewerRole 决定，后端出）
  birthDate: string; deathDate: string;
  epitaph: string;           // 一行截断由前端做
  avatarUrl: string;
  candleLit: boolean;        // 该人物 24h 窗口内是否有人祭扫
  pos: { x: number; y: number }; // 灯位（0~1 相对坐标），来自 halls.layout_json
}
```

**页面消费规则**：
- `lamps.length === 1` → 进入即聚焦该灯，表现同现有单人馆页。
- 拖拽摆位入口仅 `owner` 可见；摆位写回走 `PATCH /api/halls/[id]/layout`（仅 owner，服务端校验）。
- 聚焦某灯后，人物详情数据复用 F1–F6 既有视图（按 `memorialId` 取数），本视图不重复下发内容数据。
- `HallView` 同样遵守前端红线：无访问量、无热度字段。

## F8. 星海视图 `GardenSeaView` — 纪念园（2026-08-23 新增，墓园规格 §8）

```ts
interface GardenSeaView {
  halls: StarClusterView[];   // 仅 in_garden=1 且 public 的馆；按星域分片下发
}
interface StarClusterView {
  hallId: string;
  nameMasked: string;         // 馆名/单人馆逝者名，已脱敏
  x: number; y: number;       // 星海坐标（halls.garden_x/garden_y）
  zone: 'public' | 'family' | 'official';
  lampCount: number;          // 馆内人数（星群规模）
  candleLit: boolean;         // 24h 窗口内任一人物有祭扫
  avatarUrl: string;          // 抽屉卡片摘要用（单人馆头像/多人馆首灯）
  birthDate: string; deathDate: string; epitaph: string; // 单人馆摘要；多人馆回落馆训
  constellationOf: string | null; // 所属祠堂 id（M4 前恒 null，前端不渲染连线）
}
```

**页面消费规则**：
- LOD：远端星群只消费 `x/y/candleLit/lampCount` 合并渲染光晕；进入视口阈值后才取完整字段（分片参数 `?zone=&bbox=`）。
- 搜索/筛选走既有 `GET /api/garden?q=`，不匹配星群前端降亮不隐藏。
- 择位/连线渲染规则见墓园规格 §8.3；热度、访问量字段不存在于本视图（红线）。

## F9. 角色音色视图 `VoiceProfileView` — 对话朗读与角色创建（2026-08-23 新增，FR-13/14）

```ts
interface VoiceProfileView {
  mode: 'none' | 'preset' | 'design' | 'clone'; // none=未配置，用系统默认音色
  voice: string;            // preset：预置音色名；design/clone：服务端音色句柄
  voiceDesc: string;        // design 档的描述原文（回显用，打码规则同人名）
  cloneStatus: '' | 'pending' | 'approved' | 'rejected'; // 仅 clone 档有效
  updatedAt: string;
}
```

**页面消费规则**：
- 对话侧板 🔊 只读消费：`mode/voice`（`clone` 且 `cloneStatus='approved'` 才用复刻音色，否则回落默认音色）。
- 审核中（`pending`）时角色创建/设置页显示「声音审核中」；`rejected` 显示驳回原因并允许重传。
- 以复刻音色朗读时，前端据此渲染「AI 合成声音」角标（视图层不下发角标开关，由 `mode==='clone' && approved` 推导）。
- 本视图并入 F1/F5 既有下发（`GET /api/memorials/[id]` 带 `voiceProfile` 字段），不单开查询接口；写路径见 08 §3.14。

## 前端通用规则

1. 所有列表必须处理 **空 / 加载 / 错误** 三态（设计流程 §一-6）。
2. 打码只在后端做；前端拿到的 `senderMasked`/`nameMasked` 直接渲染。
3. 时间一律 UTC 进、本地时区 + 相对时间出。
4. 权限相关 UI 一律以视图中的 `viewerRole` 为准，不做本地推断。

# 下篇 · 后端数据设计（物理存储层）

> 引擎：SQLite（`data/bian.db`，better-sqlite3）；迁移走 `tools/db-migrate.mjs`（版本化、可回滚、`-- @add-column` 指令支持）。
> 约定：主键 `TEXT`（uuid）；时间 `TEXT` UTC ISO；金额 `INTEGER` 分；布尔 `INTEGER 0/1`；审核统一 `review_status(approved/pending/rejected)` + `review_reason`；红线 = 无虚拟币/积分/排行榜任何字段。

## B0. ER 总览

```
users ──< sessions / login_codes / auth_oauth_states / orders / ai_generation_jobs / data_requests / moderation_appeals
orders ──< payment_events
ai_generation_jobs ──> items（claim 后）
memorials ──< life_events / memories / messages / tributes / chat_messages / media / customizations
halls ──< memorials（合馆：一馆多人，memorials.hall_id，2026-08-23 新增，见 B17）
tributes >── items
memorials >──< groups（memorial_groups）──< group_members >── users
memorials ──< digital_humans（暂缓）
prompt_quota（每日限量）· events（埋点）
```

**视图模型 → 物理表装配关系**（后端职责，前端无感）：

| 视图模型 | 装配来源 |
|---|---|
| F1 MemorialView | `memorials` + `tributes`(is_burning, 24h 窗口推断 candleLit) |
| F2 TimelineItem | `life_events`（+ `media`，待确认⑨） |
| F3 FeedItem | `tributes ⋈ items` ∪ `messages ⋈ users`，排序截断 50，输出层 `maskName` |

| F7 HallView | `halls` + `memorials`(hall_id) + `tributes`(分人 candleLit 推断)；摆位读写 `halls.layout_json` |

## B12. 账号族 ✅ 已有（001/002/004/006）· 2026-08-24 拍板「登录/注册分离」后补全文档

- `users(id PK / email UNIQUE / phone / wechat_openid / wechat_unionid / avatar_url / name / membership_tier='free' / membership_expires_at / stripe_customer_id / settings / created_at)`
  - `phone`、`wechat_openid`、`wechat_unionid` 均带**部分唯一索引**（`WHERE 非空`，002/006 落地）：既是防重约束，也是登录/注册分流时「账号存在性判定」的依据（注册查占用、登录查命中，见 08 §3.0 `intent` 契约）。
  - 一行账号可同时持有多登录方式（手机/邮箱/微信），互不冲突；`POST /api/auth/bind` 绑定、`DELETE` 解绑（最后一种登录方式拒解，`409 last_login_method`）。
- `sessions(token PK / user_id / expires_at)`：Cookie 会话，登录/注册成功后同路写入，不分流。
- `login_codes(channel/target/code/expires_at/attempts/used/request_ip/locked_until)`：验证码，发码阶段不区分登录/注册意图，限频与锁定沿用。
- `auth_oauth_states(state PK / user_id / provider / expires_at)`（已实现，本次补录）：微信扫码 OAuth 一次性 state（10 分钟）；`user_id` 非空 = 登录态发起的「绑定」流程；**迁移 M11 加 `intent` 列**区分扫码目的是登录还是注册（决定 callback 未匹配账号时建号还是拒绝，见 08 §3.0）。
- **登录/注册分离零新增账号表**：注册 = `users` 新行（手机号通道带 `phone`、邮箱通道带 `email`、微信通道带 `wechat_openid/wechat_unionid/avatar_url`，三通道平级）；`name` 缺省「彼岸用户」；协议勾选不落库、由 `events` 埋点（`register`）留痕。

## B16. 新增表结构说明（2026-08-23，R5 配套）

- `notifications`：通知中心（审核结论/协作动态/系统）。写入点统一 `lib/notify.ts` 的 `insertNotification(userId, kind, title, link)`；查询 `GET /api/me/notifications` 倒序上限 50。
- `feedback`：帮助与反馈表单落库；同 UGC 约定走 `review_status`；同用户 60s 限频在应用层。
- `users.settings`：JSON 串与默认值 `{notifyReview:true, notifyCollab:true, privateDefault:false}` 读取时合并，不回填。
- `memorials.deleted_at`：软删后所有馆查询统一补 `AND deleted_at=''`（集中在 `lib/memories.ts getMemorialForAccess` 一处）；关联数据保留 30 天由离线任务物理清理。

## B17. 合馆「长明灯阵」表结构（2026-08-23 新增，FR-02b 配套）

> 依据：`docs/13-馆内多人合馆（长明灯阵）展示方案.md` §7。一馆多人（1~6 位逝者），馆级实体独立成表。

**新表 `halls`**（馆级实体）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | uuid |
| name | TEXT NOT NULL | 馆名（如「张氏家族纪念馆」） |
| motto | TEXT DEFAULT '' | 馆训一句话 |
| skin | TEXT DEFAULT 'lanterns' | 场景皮肤：`lanterns`（长明灯阵）/ `ancestral`（祠堂牌位墙，备选） |
| layout_json | TEXT DEFAULT '{}' | 馆内灯位摆位 JSON：`{memorial_id: {x, y}}`，馆主拖拽持久化 |
| in_garden | INTEGER DEFAULT 0 | 是否入纪念园星海（1=入园；仅 public 馆可为 1） |
| garden_x / garden_y | REAL | 星海园级择位坐标（0~1 相对坐标）；NULL=未择位待自动补位 |
| garden_zone | TEXT DEFAULT 'public' | 星域：`public`（普通）/ `family`（家族）/ `official`（名人，仅平台馆） |
| visibility | TEXT NOT NULL | 三级可见性，馆级统一、人物继承 |
| user_id | TEXT NOT NULL | 馆主 |
| review_status / review_reason | TEXT | 建馆审核，沿用统一约定 |
| created_at / updated_at | TEXT | |

**`memorials` 加列**：`hall_id TEXT DEFAULT ''`（空串 = 迁移前存量，由回填脚本补齐）。索引 `idx_memorials_hall(hall_id)`。

**归属链路**：`halls 1—N memorials`；`life_events / memories / messages / tributes / chat_messages / media` 仍挂 `memorial_id`（人物级）不动；馆级聚合（全馆留言墙、合祭）按 `memorials.hall_id` JOIN。合祭一次动作产生 N 条 `tributes`，以同一 `order_id`（付费）或应用层批次号（免费）关联。

**迁移（M8）**：为每个存量 `memorials` 行创建同名 `halls` 行并回填 `hall_id`；存量期 `halls.id` 可直接复用 `memorials.id`（一一对应期 URL 零变更），合馆新建时再发新 uuid。存量馆对外 URL 与行为不变（N=1 特例）。可回滚：回填脚本幂等，删列前仅弃用读取。

**迁移（M9，星海配套）**：`halls` 加 `in_garden / garden_x / garden_y / garden_zone` 四列；`in_garden=1` 必须满足所属馆 `visibility='public'`（应用层强制）。家族星座连线不落库——M4 祠堂上线后由族谱关系实时推导。

**红线核对**：`halls` 表无访问量、无热度、无排行字段；灯样式装饰主题走既有 `items/orders` 一口价链路，不新增支付概念。

## B18. 语音能力表结构（2026-08-23 新增，FR-13/14 配套）

> 依据：`docs/14-语音能力方案.md` §2.3/§5。语音输入/朗读不改消息模型（落库仍是文字）；变更只在角色音色配置上。

**`memorials` 加列**（角色音色档案，一人一档案）：

| 字段 | 类型 | 说明 |
|---|---|---|
| voice_mode | TEXT DEFAULT '' | `''`（未配置）/ `preset` / `design` / `clone` |
| voice_handle | TEXT DEFAULT '' | preset=预置音色名；design/clone=MiMo 侧音色句柄（服务端生成，前端不解析） |
| voice_desc | TEXT DEFAULT '' | design 档的自然语言描述原文（回显用，输出层同人名打码） |
| voice_updated_at | TEXT DEFAULT '' | |

**新表 `voice_clones`**（B 档音色复刻申请，UGC 审核约定）：

| 字段 | 类型 | 说明 |
|---|---|---|
| id | TEXT PK | uuid |
| memorial_id | TEXT NOT NULL | 所属人物（馆级不挂，音色是人物级资产） |
| user_id | TEXT NOT NULL | 提交人（须为该馆 owner/collaborator，服务端校验） |
| sample_url | TEXT NOT NULL | 声音样本对象存储路径（**实现差异**：样本由 voice 路由直接收 multipart 落 `voice/` 子目录，不走 /api/upload + media_id——该接口仅图片） |
| consent_accepted | INTEGER NOT NULL DEFAULT 0 | 近亲属授权声明勾选；0 时应用层拒绝提交（对齐 digital_humans.consent 约定） |
| review_status / review_reason | TEXT | 沿用 UGC 统一约定：pending/approved/rejected；进 admin 审核队列（`review_voice_clone` 动作） |
| reviewed_by / reviewed_at | TEXT | 审核留痕 |
| created_at / updated_at | TEXT | |

**状态联动**：`voice_clones` approved 后才允许 `memorials.voice_mode='clone'` 生效（应用层强制）；rejected 保留记录供重传对照。样本文件按隐私政策限期删除（对齐备案材料 §4.3 素材删除口径）。

**迁移（M10）**：`memorials` 加 `voice_mode / voice_handle / voice_desc / voice_updated_at` 四列 + 新建 `voice_clones` 表；存量行 `voice_mode=''`（未配置，朗读用默认音色，行为不变）。可回滚：删列前仅弃用读取。

**红线核对**：语音链路不新增消息字段、不落库识别音频；`voice_clones` 无公开查询接口（仅本人与审核员可见）；全表无访问量/热度字段；复刻音色气泡的「AI 合成声音」标识由视图层推导（F9），不需落库开关。

## B15. 一致性与红线核对

1. 打码只在输出层（`maskName`），库内原文。

5. UGC 四表（memories/messages/tributes/media + items 生成物）统一 `review_status` 约定，申诉走 `moderation_appeals`。
