## 一、架构速览

```
浏览器 → 公网IP:80 (Nginx) → 127.0.0.1:3002 (Next.js, PM2 守护) → SQLite (/var/www/bian/data/)
```

| 组件 | 位置 / 说明 |
|---|---|
| 应用目录 | `/var/www/bian`（git 仓库，跟随 `origin/master`） |
| 进程守护 | PM2，进程名 `bian`，配置 `deploy/ecosystem.config.cjs`（**以 root 运行，pm2 命令要加 sudo**） |
| 应用端口 | **3002**（写在 ecosystem.config.cjs 的 `args` 里） |
| Nginx | 站点配置 `/etc/nginx/sites-available/bian`，软链到 `sites-enabled/`，模板在 `deploy/nginx.conf.template` |
| 数据库 | SQLite，`/var/www/bian/data/`；迁移脚本 `migrations/`，工具 `npm run db:migrate / db:verify / db:backup` |
| 备份目录 | `/var/www/bian/data/backups/` |
| 日志 | `/var/log/bian/out.log`、`/var/log/bian/error.log`，或 `sudo pm2 logs bian` |

## 二、标准发布流程（本地构建产物模式）

适用场景：本地（开发机）构建产物上传发布，服务器只运行不编译（省内存）。

### 主路径：一条龙 `npm run release`（P1-1，2026-09-07 起唯一标准）

前置：本地处于 `master` 分支且工作区干净（src/deploy/tools/migrations/package.json/next.config.ts 无未提交改动）；SSH 密钥 `~/.ssh/bian_deploy` 已打通；打包需要 GNU tar（本机 Git 为自定义安装根 `E:\AI训练\Git\Git\usr\bin`，执行前先把它加到 PATH）。

```bash
npm run release                  # == node tools/release.mjs：6 步全自动
npm run release -- --skip-sync   # 跳过与 origin/master 一致性检查（已 push 后偶用）
npm run release -- --skip-dirty  # 跳过工作区脏检查（慎用）
```

自动流程：① 前置检查（分支 / 脏区 / 与 origin/master 同步）→ ② 隔离构建 `.next-release`（`BIAN_NEXT_DIST_DIR`，免疫本地 dev server）并写入 `RELEASE_COMMIT` → ③ GNU tar 打包（约 7-8MB）→ ④ scp 上传 → ⑤ 服务器 `bash deploy/apply-release.sh` → ⑥ 线上验证（health / starsea / garden / 迁移数 / 原型屏蔽）+ 报告落盘 `deploy-reports/release-<时间>.md`。

服务器侧 apply-release.sh 自动执行：杀残留进程 → `git reset --hard origin/master` 同步代码 → `db:backup` → 保留上一版 `.next.prev` 并解包 → **产物-代码一致性校验**（包内 RELEASE_COMMIT vs git HEAD，不一致自动回滚中止，旧站不受影响）→ Turbopack 哈希别名动态补链（坑 9）→ 迁移 + 校验 → PM2 重启 + release:smoke。

**成功标志**：本地输出 `✅ 发布完成。报告：deploy-reports/release-….md`；报告含 commit / BUILD_ID / health / starsea / garden / 迁移已应用 / 原型屏蔽。

> ⚠️ 发布 = 真实改动生产站：会重启 PM2（闪断数秒），每次发布前自动 `db:backup`。包体异常 >50MB 自动中止（历史 845MB 废包事故阈值）。

### 备选：手动分包 + 服务器 apply（脚本/网络出问题时）

```bash
# 本地：构建并打包（压缩包必须放 /var/www/bian/，不是家目录；apply 解包后会删除压缩包）
npm run build
# scp 上传 bian-release-next.tar.gz 到 root@47.238.100.165:/var/www/bian/
# 服务器：
cd /var/www/bian && sudo bash deploy/apply-release.sh
```

### 回滚（一键回到上一版产物；git 代码与数据库不动）

```bash

ssh -i ~/.ssh/bian_deploy root@47.238.100.165 'bash /var/www/bian/deploy/rollback.sh --list'
# 一键回滚产物（.next.prev ↔ .next + PM2 重启 + 冒烟）

# 需要连数据库一起回滚：按 --list 选备份 → cp 备份 data/bian.db → pm2 restart bian（见 §七）
```

## 三、踩坑记录（真实踩过，2026-08-23 ~ 09-07）

### 坑 1：压缩包解压到了错误的目录
- **现象**：在家目录下执行 `tar -xzf`，`.next` 解到了家目录。
- **后果**：应用不会因此运行；家目录残留几百 MB 垃圾。
- **正确做法**：压缩包放 `/var/www/bian/` 再解（或直接用 apply-release.sh，它自己在正确目录解包）。误解压后清理：`rm -rf ~/.next`。
- **认知纠偏**：`tar` 解压成功 ≠ 应用运行成功。运行需要 迁移 → PM2 重启 → 冒烟 全链路。

### 坑 2：多条命令一次粘贴导致粘连、命令被吞
- **现象**：`sudo git reset --hard origin/master` 和 `remote: Enumerating objects...` 粘成一行，reset 实际没执行；后续排查才发现文件不存在。
- **正确做法**：**逐条粘贴，等提示符 `$` 出来再贴下一条**；或者把多步合成一行用 `&&` 连接。判断是否执行成功的依据是输出（如 reset 必有 `HEAD is now at xxxxxxx`），不是"没报错"。

### 坑 3：服务器 node_modules 缺依赖（better-sqlite3）
- **现象**：apply-release.sh 卡在 [3/6] 备份，`Error: Cannot find package '.../better-sqlite3/index.js'`。
- **原因**：`package.json` 新增过依赖，服务器没重装。apply-release.sh 不装依赖（省时间），依赖需手动保证。
- **修复**：
  ```bash
  cd /var/www/bian
  sudo npm install
  ```
  若 `better-sqlite3` 编译失败（原生模块），先装编译环境：`sudo apt-get install -y build-essential python3`，再重试。
- **预防**：每次 `package.json` 有依赖变更的发布，先 `sudo npm install` 再跑发布脚本。

### 坑 4：冒烟脚本端口与服务端口不一致（误报失败）
- **现象**：服务实际正常，但冒烟全部 `fetch failed`。
- **原因**：`tools/release-smoke.mjs` 默认 `http://localhost:7300`，而服务跑在 3002。
- **修复（已提交 c552043）**：脚本默认端口已改为 3002。也可用环境变量覆盖：
  ```bash
  sudo BASE_URL=http://localhost:3002 npm run release:smoke
  ```
- **教训**：看到冒烟失败，先 `curl http://localhost:3002/api/health` 直接探应用，区分"应用真挂了"还是"检查脚本指错地方"。

### 坑 5："端口被占用"的误判 + pm2 restart 不生效
- **现象**：以为 3002 被别的程序占用想换 3003；`sudo ss -ltnp | grep 3002` 显示占用者是 `next-server`——**就是应用自己**。
- **认知纠偏**：换端口前先 `ss -ltnp` 看占用者是谁。PM2 管的应用重启后仍占着原端口，这是正常的。
- **关联坑**：改 `ecosystem.config.cjs` 里的端口/启动参数后，`pm2 restart` **不会**读取新参数，必须：
  ```bash
  sudo pm2 delete bian
  sudo pm2 start deploy/ecosystem.config.cjs --env production
  sudo pm2 save
  ```
  （本案最终确认无需换端口，已回退，端口维持 3002。）

### 坑 6：Nginx 没配置，外网 404
- **现象**：应用直连 3002 正常（`app-zh: 200`），但访问 80 端口 404。
- **原因**：`/etc/nginx/sites-enabled/` 里没有 bian 站点配置，请求落到了默认站点。
- **修复**：
  ```bash
  cd /var/www/bian
  sudo cp deploy/nginx.conf.template /etc/nginx/sites-available/bian
  sudo ln -sf /etc/nginx/sites-available/bian /etc/nginx/sites-enabled/bian
  sudo rm -f /etc/nginx/sites-enabled/default
  sudo nginx -t && sudo systemctl reload nginx
  ```
- **另一个小坑**：`curl http://localhost/zh` 可能因 `localhost` 解析到 IPv6 返回 404/异常，**测试用 `http://127.0.0.1/zh`**，不影响外网真实访问。

### 坑 7：域名"打不开"——浏览器自动跳 HTTPS，而 443 没配
- **现象**：HTTP 访问正常，用户浏览器输域名却打不开。
- **原因**：现代浏览器会把裸域名自动升级为 `https://`，而 Nginx 只配了 80 端口，443 无监听 → 连接失败。
- **修复**：配置 HTTPS（见下节）。
- **排查方法**：`curl -s -o /dev/null -w '%{http_code}\n' https://域名/zh` 返回 000 = HTTPS 未配置；同时用 `dig +short 域名 @223.5.5.5` 对比服务器公网 IP（`curl -s ifconfig.me`）确认 DNS 指向正确。

### 坑 8：发布后"代码没更新"——游离 next-server 占住 3002（2026-08-25 实录）
- **现象**：`deploy.sh`（旧服务器自构建发布脚本，2026-09-07 已删除）全程成功、冒烟 PASS，但验证新接口行为仍是旧逻辑（如 verify 仍返回 `invalid_code` 而非 `missing_intent`）；改了 `.env.production` 也不生效。
- **原因**：历史上某次手动 `npm start` 留下的 next-server 进程没被 pm2 管理，一直占着 3002；pm2 `restart` 的子进程 EADDRINUSE 起不来，网站始终由僵尸进程用**旧代码 + 旧环境变量**应答。旧的 `deploy.sh` 原本不清理残留进程（`apply-release.sh` 有 pkill）。
- **排查**：`sudo ss -ltnp | grep 3002` 看 `users:(("next-server",pid=X))`，与 `pm2 pid bian` 对比——不一致即中招。
- **修复**：`sudo kill <旧pid> && pm2 restart bian`。已防复发：`apply-release.sh` 第 1 步先 `pkill -f next-server` 清残留。

### 坑 9：npm ci 清掉 Turbopack 原生模块哈希别名 → 全站 500（2026-08-26 实录）
- **现象**：发布脚本全部成功、PM2 online，但所有请求 500；`/var/log/bian/error.log` 反复出现 `Failed to load external module better-sqlite3-90e2652d1716b047: Cannot find module`（或 `sharp-20c6a5da84e2135f`）。
- **原因**：Turbopack 生产构建把 `serverExternalPackages` 里的原生模块（better-sqlite3、sharp）按 `<包名>-<16位hex>` 别名外部化，chunk 里是字面量 `require("better-sqlite3-<hash>")`；该别名历史上由服务器早期构建留在 `node_modules/` 里（软链），**`npm ci` 重建 node_modules 时会把这两个"陌生包"清掉**，本地构建产物一到服务器就解析不到别名。另注意 2G 内存机上直接服务器构建（旧 deploy.sh 模式）易 OOM 卡死（需先加 2G swap：`fallocate -l 2G /swapfile && chmod 600 /swapfile && mkswap /swapfile && swapon /swapfile`）。
- **排查**：`grep -rhoE '[a-zA-Z@/._][a-zA-Z0-9@/._-]*-[0-9a-f]{16}' .next/server/chunks/*.js | sort -u` 列出构建实际引用的全部哈希别名，再对照 `ls node_modules/`。
- **修复**：手工补链 `sudo ln -sfn node_modules/<真包名> node_modules/<包名>-<hash>` 后 `pm2 restart bian`。已防复发：`apply-release.sh`（步骤 4.5）按 `.next` 实际引用**动态补链**，任何 `npm ci` 之后的发布都自动修复。

## 五、域名与 HTTPS（已上线：bianmuyuan.cn）

2026-08-23 已配置完成，当前状态：

- 域名 `bianmuyuan.cn` → `47.238.100.165`（本服务器）
- Let's Encrypt 证书：`/etc/letsencrypt/live/bianmuyuan.cn-0001/`，**certbot 定时任务自动续期**，无需手动维护
- Nginx 线上配置由 certbot 改写：80 端口 **301 跳转 HTTPS**，443 提供 SSL 服务
- ⚠️ **不要再用 `deploy/nginx.conf.template` 覆盖 `/etc/nginx/sites-available/bian`**（会丢掉 SSL 配置）；模板仅用于全新服务器首次安装

### 首次配置 HTTPS 的步骤（备查）

```bash
sudo apt-get install -y certbot python3-certbot-nginx
sudo ufw allow 443/tcp        # 同时到阿里云控制台安全组放行 443
# server_name 必须是真实域名，否则 certbot 报 "Could not automatically find a matching server block"
sudo sed -i 's/server_name _;/server_name bianmuyuan.cn;/' /etc/nginx/sites-available/bian
sudo nginx -t && sudo systemctl reload nginx
sudo certbot --nginx -d bianmuyuan.cn   # 已有证书时选 1 reinstall；跳转选 2 Redirect
```

验证：`curl -s -o /dev/null -w '%{http_code} %{redirect_url}\n' http://bianmuyuan.cn/zh` 应返回 `301 https://...`。

## 六、防火墙 / 安全组 checklist

外网打不开时按顺序查：

1. 应用层：`curl -s -o /dev/null -w '%{http_code}\n' http://127.0.0.1/zh`（服务器本机 200 = 应用和 Nginx 都没问题）
2. 系统防火墙：`sudo ufw status`（应有 `80/tcp ALLOW`；没有则 `sudo ufw allow 80/tcp`）
3. **阿里云控制台安全组**：ECS 实例安全组需放行 80（和后续 443）端口——这一步只能在网页控制台操作，最容易被忘。
