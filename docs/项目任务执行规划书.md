# 彼岸项目任务执行规划书

> 版本：v1.0  
> 编制日期：2026-08-15  
> 适用范围：彼岸线上纪念平台从当前 MVP 推进至可正式发布、可持续运营的完整产品  
> 技术基线：Next.js 16、React 19、TypeScript 7、better-sqlite3、Stripe、Three.js

## 1. 规划目标

本规划用于统一彼岸项目后续的功能开发、视觉提升、工程治理、安全运维和发布验收工作。执行时以可独立交付、可验证、可回归为原则，避免按页面零散开发或在上线前集中补救质量问题。

项目最终目标：

1. 完成账号、纪念馆、家庭群组、媒体、生平、祭奠、开放墓园、会员和数字人业务闭环。
2. 建立具有辨识度、情感表达克制且一致的视觉体验。
3. 将本地 MVP 架构升级为具备安全、迁移、备份、监控和扩展能力的生产系统。
4. 完成真实第三方服务、支付、内容审核与合规流程接入。
5. 建立自动化测试、视觉回归和上线回滚机制。

## 2. 当前项目基线

### 2.1 已完成能力

- 邮箱和手机验证码登录、服务端会话。
- 纪念馆创建、三级可见性和群组授权。
- 家庭群组创建、邀请码加入。
- 图片与视频上传、媒体画廊、受限 Markdown 生平、人生时间轴。
- 官方祭品、自定义祭品、AI 祭品生成和献祭留言。
- 2D/3D 公共墓园与墓位安放。
- 会员页面、Stripe Checkout 和数字人重做付费入口。
- 数字人素材向导、mock 任务、审核和展示流程。
- 管理后台、基础埋点、中英双语、隐私政策和用户协议。

### 2.2 已验证状态

- `npm run build` 通过，当前共生成 39 个应用与 API 路由。
- P1 核心业务 smoke test 通过 27/27。
- P4 数字人 smoke test 通过 18/18。
- P2 核心业务可用，但有 1 条公共墓园 UI 断言与当前页面不一致。
- smoke test 使用固定账号，并发运行会触发验证码限流，尚不具备稳定并行回归条件。

### 2.3 主要缺口

- 微信扫码登录、账号绑定和冲突账号合并尚未实现。
- 群组缺少成员管理、退出、转让和解散能力。
- 媒体库缺少排序、修改配文、设封面和批量任务反馈。
- 图片审核和完整人工审核队列尚未闭环。
- AI 祭品与数字人仍有 mock 或接入占位逻辑。
- Stripe 缺少订阅取消、支付失败、退款和完整幂等处理。
- SQLite、本地文件存储和进程内异步任务不适合多实例生产部署。
- 自动化测试、安全防护、监控、备份和发布回滚仍需系统建设。
- 视觉已具备基础风格，但首页、纪念馆、墓园、祭品资产和移动端仍需统一润色。

## 3. 执行原则

1. 先建立稳定测试和数据安全，再扩展核心业务。
2. 功能与视觉同步推进，每个用户功能同时验收可用性和画面表现。
3. 第三方服务先完成 POC，再锁定接口和数据模型。
4. 所有任务必须具备明确交付物和可重复执行的验收方法。
5. 生产数据变更必须使用版本化 migration，并在执行前完成备份。
6. 不以 mock 结果、手工改库或一次性脚本作为正式完成标准。
7. 3D、天气和个性化等增强能力不得阻塞首个正式版本发布。

## 6. 详细任务规划

### T01 稳定测试基线

- 优先级：P0
- 目标：让自动化回归结果稳定、可并行、可定位。
- 交付物：随机测试账号与数据、独立 cookie 和数据库清理机制、修正后的 P2 断言、统一 smoke 入口、CI 可执行命令。
- 依赖：无。
- 验收：P1、P2、P4 可连续运行 3 次；允许并行时不因共享账号触发限流；失败后仍可完成清理并输出具体断言。

#### T01.1 记录当前失败基线

- 目的：先固定当前问题，避免改造后只凭感觉判断是否有效。
- 操作：
  1. 启动开发服务：`npm run dev`。
  2. 分别运行 `node tools/smoke-p1.mjs`、`node tools/smoke-p2.mjs` 和 `$env:BASE_URL='http://localhost:3002'; node tools/smoke-p4.mjs`。
  3. 立即再次运行 P1 和 P2，记录验证码接口是否返回 `429 too_frequent`。
  4. 同时运行 P1 和 P2，记录固定账号、共享数据库和清理逻辑之间的冲突。
  5. 将需要修复的现象限定为：固定测试身份、全局 cookie jar、硬编码数据库路径、清理不进入 `finally`、P2 过期 UI 文案断言、三个脚本配置方式不一致。
- 涉及文件：`tools/smoke-p1.mjs`、`tools/smoke-p2.mjs`、`tools/smoke-p4.mjs`。
- 完成标准：能够稳定复现至少一个重复运行问题，且保留完整失败输出用于改造后对比。

#### T01.2 建立共享 smoke 工具模块

- 目的：消除三个脚本重复实现 HTTP、cookie、断言和路径逻辑造成的行为差异。
- 新建文件：`tools/smoke/support.mjs`。
- 实现内容：
  1. `createRunContext(suiteName)`：生成本次运行唯一的 `runId`，建议格式为 `<suite>-<timestamp>-<random>`。
  2. `testEmail(role)`：根据 `runId` 和角色生成唯一邮箱，例如 `smoke-p1-owner-<runId>@test.local`。
  3. `createCookieJar()`：每个测试用户返回一个独立 cookie jar，不再通过清空同一个全局 `Map` 切换身份。
  4. `createApiClient({ baseUrl, cookieJar })`：统一请求、JSON 解析、cookie 写入、超时和响应摘要。
  5. `check(name, actual, expected)` 与 `assert(condition, message, details)`：失败时输出 suite、步骤、HTTP 状态和响应片段。
  6. `waitFor(predicate, { timeoutMs, intervalMs })`：供数字人任务轮询使用，超时后抛出包含最后状态的错误。
  7. `resolveDbPath()`：从 `SMOKE_DB_PATH` 读取测试数据库路径，未配置时回退到 `data/bian.db`。
  8. `resolveBaseUrl()`：统一从 `BASE_URL` 读取服务地址，默认 `http://localhost:3002`。
- 实现约束：共享模块只处理测试基础设施，不包含 P1/P2/P4 业务断言。
- 完成标准：三个 smoke 脚本均不再各自维护 cookie 解析、BASE 常量和基础断言函数。

#### T01.3 为每次运行生成唯一测试数据

- 目的：消除验证码 60 秒限流和不同脚本删除彼此数据的问题。
- 修改文件：`tools/smoke-p1.mjs`、`tools/smoke-p2.mjs`、`tools/smoke-p4.mjs`。
- 实现内容：
  1. P1 的 owner 和 member 使用两个不同随机邮箱，不再使用 `test@example.com` 与 `test2@example.com`。
  2. P2 使用自己的随机邮箱，不与 P1 共用账号和 AI 月配额。
  3. P4 保留随机邮箱策略，但改为使用共享 `testEmail()`。
  4. 纪念馆名称、群组名称、媒体 caption 和可搜索文本附加 `runId`。
  5. 所有清理操作使用精确记录的用户 ID、纪念馆 ID、群组 ID、item ID 和任务 ID，不再使用 `LIKE 'test%@example.com'`。
- 数据示例：`smoke-p1-owner-<runId>@test.local`、`纪念馆-p1-<runId>`。
- 完成标准：P1、P2 同时请求验证码不会互相触发目标地址限流；任一脚本清理时不会删除另一个脚本的数据。

#### T01.4 隔离不同用户的会话状态

- 目的：避免 P1 通过清空和复制同一个 `Map` 切换 owner/member 时发生身份串用。
- 修改文件：`tools/smoke-p1.mjs`，共享实现位于 `tools/smoke/support.mjs`。
- 实现内容：
  1. 创建 `ownerClient`、`memberClient` 和 `anonymousClient` 三个独立 API client。
  2. owner 登录后只由 `ownerClient` 操作建馆、授权、上传和个人中心。
  3. member 登录后只由 `memberClient` 操作加入群组和访问授权纪念馆。
  4. 匿名访问统一使用不带 cookie 的 `anonymousClient`。
  5. 每次关键请求前在日志中输出逻辑身份，但不得输出 session token。
- 完成标准：删除所有手工 `cookieJar.clear()` 和 Map 复制逻辑；owner/member 权限断言仍全部通过。

#### T01.5 将清理改为可靠的 `try/finally`

- 目的：即使中途出现异常或断言失败，也能删除测试数据和上传文件。
- 修改文件：三个 smoke 脚本；新建 `tools/smoke/cleanup.mjs`。
- 实现内容：
  1. 每个 suite 建立资源登记表：`userIds`、`memorialIds`、`groupIds`、`itemIds`、`taskIds`、`uploadUrls`。
  2. 每次 API 创建成功后立即登记资源 ID，而不是等脚本末尾重新模糊查询。
  3. 主测试流程放入 `try`，清理放入 `finally`。
  4. 按外键依赖从子到父清理：数字人/额度、tribute、media、life events、memorial group、memorial、group member、group、AI quota、自定义 item、session、login code、user。
  5. 上传文件仅允许删除解析后位于 `<workspace>/data/uploads/` 内的路径，拒绝 `..`、绝对外部路径和非 `/uploads/` URL。
  6. 每项清理独立捕获错误，继续清理剩余资源；最终集中输出 cleanup warning。
  7. 数据删除使用 SQLite transaction，确保同一批数据库清理要么完成要么回滚。
- 完成标准：故意在中间断言处抛错后，数据库中找不到对应 `runId`，本次生成的上传文件也已删除。

#### T01.6 修复脆弱和过期断言

- 目的：测试业务行为，不把易变的展示文案当作唯一判断依据。
- 修改文件：`tools/smoke-p2.mjs`，必要时补充 `src/app/api/garden/route.ts` 的现有返回字段断言。
- 实现内容：
  1. 删除 `gardenPage.text.includes("松涛区")` 这条已与当前 UI 脱节的断言。
  2. 保留页面包含本次唯一纪念馆名称的用户可见结果断言。
  3. 使用 `/api/garden?q=<runId>` 验证返回记录的 `id`、`garden_section` 和 `garden_slot`，避免只检查静态中文文案。
  4. 对页面 HTML 的必要断言使用本次唯一业务数据，不依赖容易修改的标题和样式类名。
  5. 对每个创建接口先断言 HTTP 状态和响应结构，再读取 `.id`，避免前置失败后出现 `Cannot read properties of undefined`，掩盖真正原因。
- 完成标准：修改墓园分区显示文案不会导致 smoke 失败；API 不返回 ID 时测试在创建步骤立即给出清晰失败信息。

#### T01.7 统一配置和启动前检查

- 目的：消除 P1/P2 固定 3002、P4 默认 3000 的不一致，并让服务未启动时快速失败。
- 修改文件：三个 smoke 脚本、`tools/smoke/support.mjs`。
- 实现内容：
  1. 所有脚本统一读取 `BASE_URL`，默认值统一为 `http://localhost:3002`。
  2. 所有脚本统一读取 `SMOKE_DB_PATH`，不得硬编码 `E:/彼岸/data/bian.db`。
  3. 测试开始前请求一个稳定页面或 API，连接失败时输出实际 `BASE_URL` 和启动命令。
  4. 将单次 HTTP 请求设置为明确超时，例如 15 秒；数字人轮询单独使用更长总超时。
  5. 在启动摘要中输出 suite、runId、base URL 和数据库路径，不输出密钥或 cookie。
- 完成标准：仓库移动到其他目录后脚本仍可运行；端口配置错误时 15 秒内给出明确错误。

#### T01.8 增加统一 smoke 执行入口

- 目的：开发者和 CI 不再手工记忆三个不同命令。
- 新建文件：`tools/smoke/run-all.mjs`。
- 修改文件：`package.json`。
- 实现内容：
  1. `run-all.mjs` 按参数支持 `--serial` 和 `--parallel`。
  2. 使用子进程运行 P1、P2、P4，分别保留退出码和带 suite 前缀的输出。
  3. 任一 suite 失败时等待其他已启动 suite结束，再汇总失败项并以非零退出。
  4. 增加 scripts：`smoke:p1`、`smoke:p2`、`smoke:p4`、`smoke`、`smoke:parallel`。
  5. 默认 `npm run smoke` 使用串行模式，作为本地稳定入口；`npm run smoke:parallel` 专门验证隔离能力。
- 建议命令：
  - `npm run smoke:p1`
  - `npm run smoke`
  - `npm run smoke:parallel`
- 完成标准：统一入口能正确汇总三个 suite 的通过数、失败数、耗时和最终退出码。

#### T01.9 增加重复运行验证器

- 目的：将“连续运行 3 次”变成机器可执行的验收，而不是人工重复敲命令。
- 新建文件：`tools/smoke/repeat.mjs`。
- 修改文件：`package.json`。
- 实现内容：
  1. `repeat.mjs` 接收 `--count`，默认 3。
  2. 每轮调用统一 smoke 入口，记录轮次、耗时和退出码。
  3. 任一轮失败立即标记整体验收失败，但仍输出此前轮次摘要。
  4. 增加 `smoke:repeat` 命令，默认执行 `node tools/smoke/repeat.mjs --count 3`。
- 完成标准：`npm run smoke:repeat` 连续三轮全部通过，数据库和上传目录中无本次测试残留。

#### T01.10 接入 CI 质量门槛

- 目的：保证后续代码提交不会悄悄破坏已有主链。
- 新建文件：`.github/workflows/ci.yml`；若实际代码托管平台不是 GitHub，则创建等价流水线配置。
- 实现内容：
  1. 使用仓库 lockfile 执行 `npm ci`。
  2. 执行 `npm run build`。
  3. 使用测试环境变量启动服务，并轮询 `http://localhost:3002/zh/login`，确认服务 ready。
  4. 执行 `npm run smoke` 作为必须通过项。
  5. 在独立 job 或后续步骤执行 `npm run smoke:parallel`，验证测试隔离。
  6. 无论成功或失败都停止服务进程，并在失败时保留应用日志和 smoke 输出。
  7. CI 不配置真实 SMTP、短信、Stripe、AI 或数字人密钥，测试必须使用开发回显和 mock provider。
- 完成标准：正常分支流水线全绿；故意破坏一个 API 状态码后流水线明确失败在对应 suite 和步骤。

### T02 数据库迁移体系

- 优先级：P0；依赖：T01。
- 目标：把 `src/lib/db.ts` 中启动时执行的零散 `ALTER TABLE` 改成可追踪、可回滚的迁移系统。
- 实现步骤：
  1. 新建 `migrations/`，按 `001_initial.sql`、`002_auth.sql`、`003_media.sql` 编号拆出现有 schema。
  2. 新建 `schema_migrations(version, applied_at, checksum)`，启动时只执行未应用版本。
  3. 新建 `tools/db-migrate.mjs`，支持 `up`、`status`、`backup`、`verify`；迁移使用 transaction。
  4. 将 `getDb()` 改为只打开连接并调用 migration runner，删除静默吞掉异常的 `try/catch ALTER`。
  5. 为现有 `data/bian.db` 生成备份，执行升级并核对表、索引、行数和外键。
- 主要文件：`src/lib/db.ts`、`migrations/*`、`tools/db-migrate.mjs`、`package.json`。
- 验收命令：`node tools/db-migrate.mjs status`、`node tools/db-migrate.mjs verify`、`npm run build`。
- 完成标准：空库可初始化，旧库可升级；重复执行无变化；故意制造 SQL 错误时事务回滚且版本不被记录。

### T03 认证与基础安全加固

- 优先级：P0；依赖：T01。
- 目标：保护验证码、会话和登录接口，避免暴力尝试、枚举和会话泄露。
- 实现步骤：
  1. 在 `login_codes` 增加 `request_ip`、`attempts`、`locked_until`，为目标地址/IP建立限流查询。
  2. 修改 `request-code`：同目标 60 秒、同 IP 日限额；生产环境删除 `devCode` 响应。

6. 管理后台：保持克制、紧凑和高信息密度，不追求场景化装饰。

## 10. 任务完成定义

单个任务只有同时满足以下条件才可标记完成：

- 实现已合入当前工作分支，且没有遗留 TODO 占位。
- 新增或修改行为具备对应自动化测试。
- `npm run build` 通过，相关 smoke 或 E2E 通过。
- 权限、失败、空数据、加载和移动端状态已处理。
- 中英文文案同步更新，无乱码和文本溢出。
- 涉及视觉的任务完成桌面与移动端截图验收。
- 涉及数据的任务已验证迁移、备份和恢复路径。
- 涉及第三方服务的任务已验证超时、重试、幂等和故障补偿。
- 环境变量示例和实际部署配置保持一致，仓库中不包含密钥。

## 11. 发布门槛

正式发布前必须满足：

- P0、P1 缺陷清零，没有已知越权或数据丢失问题。
- 核心 E2E、API、smoke 和视觉回归全部通过。
- 支付、会员、AI 生成和数字人使用真实沙箱或正式测试账号验证。
- 数据库和对象存储备份恢复演练通过。
- 监控、日志、health check 和关键告警已启用。
- 隐私政策、用户协议、数据删除和 AI 标识流程与实际实现一致。
- 发布和回滚步骤至少演练一次。

## 12. 风险与外部依赖

| 风险或依赖 | 影响 | 应对方式 |
| --- | --- | --- |
| 微信开放平台资质 | 阻塞微信扫码登录 | 邮箱和手机通道先上线，微信能力独立验收 |
| 数字人供应商选择 | 影响效果、成本和合规 | 先做小规模 POC，统一 provider adapter 后再锁定供应商 |
| 深度合成备案周期 | 可能阻塞数字人正式开放 | 与技术接入并行启动，不等开发结束后再申请 |
| SQLite 与本地上传 | 限制多实例部署和容灾 | 在正式流量前完成 T12，迁移工具先于生产切换验证 |
| 内容审核服务故障 | 可能导致风险内容公开 | 高风险内容默认进入人工审核，不使用无提示 fail-open |
| 视觉增强影响性能 | 移动端卡顿或 3D 空白 | 建立质量档位、资源预算和 2D 降级模式 |
| 支付事件重复或丢失 | 重复发权益或会员状态错误 | webhook 幂等、事件落库、定时对账和补偿任务 |

## 13. 进度管理建议

- 看板状态统一使用：待开始、进行中、待验收、已完成、阻塞。
- 每个迭代只允许一个明确主目标，优先关闭已开始任务。
- 每周检查一次依赖、风险、测试稳定性和生产准备度。
- 每个里程碑结束时执行完整 build、smoke、E2E 和关键页面截图。
- 需求调整时优先修改本规划的任务范围和验收条件，再进入实现。
